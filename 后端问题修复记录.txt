问题 1（P0 · 严重 bug）：缺少 sub 的 JWT 会导致 500 错误
------------------------------------------------------------
【文件】dependencies.py  get_current_user 函数

【问题描述】
  解析 JWT 时使用 int(payload.get("sub"))，当 token 合法但缺少 "sub"
  字段时，int(None) 会抛出 TypeError。而 except 只捕获了 (JWTError, ValueError)，
  TypeError 未被捕获，最终返回 500 内部错误，而不是应有的 401 未认证。

【问题原因】
  - payload.get("sub") 在字段缺失时返回 None
  - int(None) 抛 TypeError
  - TypeError 不在异常捕获范围内

【解决方法】
  先判断 sub 是否为 None，为 None 时抛出 401 异常；否则再 int(sub) 转换。

  修改前：
      user_id = int(payload.get("sub"))
      if user_id is None:
          raise credentials_exception

  修改后：
      sub = payload.get("sub")
      if sub is None:
          raise credentials_exception
      user_id = int(sub)

【验证】
  用无 sub 字段的合法 token 请求受保护接口，返回 401（修复前为 500）。

问题 2（P2 · 设计一致性）：Application.status 使用字符串 + 手动校验
------------------------------------------------------------
【文件】schemas.py、applications.py

【问题描述】
  投递状态 status 在 models.py 中为字符串列，schema 中也是 str，合法性校验
  散落在 applications.py 里通过手动比对白名单实现，与 Role 字段使用枚举的
  规范写法不一致，且校验逻辑分散、易遗漏。

【问题原因】
  - 状态字段未像 Role 一样定义为枚举
  - 合法性校验依赖手写 if 判断，而非类型系统自动完成

【解决方法】
  1. 在 schemas.py 新增 ApplicationStatus(str, Enum) 枚举：
     applied / screening / interview / offer / rejected

  2. ApplicationOut.status 与 ApplicationStatusUpdate.status 的类型
     由 str 改为 ApplicationStatus，非法值由 Pydantic 自动拦截（返回 422）。

  3. 删除 applications.py 中的手动白名单校验：
     原：
        allowed_statuses = {"screening", "interview", "offer", "rejected"}
        if status_data.status not in allowed_statuses:
            raise HTTPException(400, "无效的状态值")
        application.status = status_data.status
     改为：
        application.status = status_data.status.value

  4. 补充 field_validator 校验器：HR 不能把状态改回 applied（applied 是投递时的初始态），
     保持原有业务语义。

【验证】
  - 传入 "screening" 正常通过
  - 传入 "xxx"（非法枚举值）返回 422
  - 传入 "applied" 被校验器拦截返回 422

问题 6（P2 · 功能完善）：列表接口缺少分页
------------------------------------------------------------
【文件】schemas.py、pagination.py（新增）、jobs.py、applications.py

【问题描述】
  list_jobs / my_applications / list_job_applications 三个列表接口
  均一次性返回全部数据（select(...).scalars().all()），数据量增大后：
  - 接口响应体积大、耗时高，前端加载慢
  - 数据库一次拉取全表，内存与连接占用高
  - 缺少统一的翻页约定，前端无法按页请求

【问题原因】
  列表接口只做全量查询，未提供分页查询参数，也未做返回结构上的分页约定。

【解决方法】
  1. 在 schemas.py 新增分页查询参数模型 PageParams（page / page_size，
     默认 1 / 10），用 field_validator 做边界校验（page>=1，1<=page_size<=100），
     并暴露 offset 属性 = (page-1)*page_size；非法值由 Pydantic 拦截返回 422。

  2. 在 schemas.py 新增泛型分页响应结构 Page[T]，字段为
     items / total / page / page_size / pages，各列表接口统一使用它作为返回结构。

  3. 新增 pagination.py 提供两个复用函数，避免每个接口重复写 count + offset/limit：
     - paginate(db_session, stmt, params)：对任意 select 语句先 count 总数，
       再 offset/limit 取当前页，返回 (items, total)
     - build_page(items, total, params)：组装成 Page 响应字典（pages 用 ceil 向上取整）

  4. 三个接口的响应类型由 List[X] 改为 Page[X]，签名中加入
     params: PageParams = Depends() 作为查询参数，内部调用 paginate/build_page。

  修改前（以 list_jobs 为例）：
      @router.get("", response_model=List[JobOut])
      async def list_jobs(db_session: AsyncSession = Depends(get_db_session)):
          result = await db_session.execute(select(Job).order_by(Job.created_at.desc()))
          return result.scalars().all()

  修改后：
      @router.get("", response_model=Page[JobOut])
      async def list_jobs(
          params: PageParams = Depends(),
          db_session: AsyncSession = Depends(get_db_session)
      ):
          stmt = select(Job).order_by(Job.created_at.desc())
          jobs, total = await paginate(db_session, stmt, params)
          return build_page(jobs, total, params)

【验证】
  - 分页参数校验：page=0 → 422；page_size=101 → 422；page_size=0 → 422；
    page=2&page_size=5 → offset=5，正常通过。
  - OpenAPI 文档中三个 GET 接口的 query 参数包含 page / page_size，
    响应结构为 items/total/page/page_size/pages，字段齐全且 items 元素类型正确
    （Page_JobOut_ / Page_ApplicationOut_）。
  - 应用可正常启动（虚拟环境 .venv 下导入 main 通过，路由正常注册）。

问题 7（P1 · 严重 bug）：分页参数非法值返回 500 而非 422
------------------------------------------------------------
【文件】jobs.py、applications.py（schemas.py 的 PageParams 不变）

【问题描述】
  三个列表接口用 params: PageParams = Depends() 声明分页查询参数。
  传入非法分页值（page=0 / page_size=101 等）时，PageParams 的
  field_validator 抛出的 pydantic ValidationError 不会被 FastAPI 捕获，
  而是作为未处理异常向上抛出，最终返回 500 内部错误，而非应有的 422。
  该行为与问题 6 的【验证】结论（"非法值返回 422"）不符。

【问题原因】
  Depends() 会把 Pydantic 模型当作普通可调用依赖：solve_dependencies 中
  通过 run_in_threadpool(call, **values) 直接实例化 PageParams，模型构造
  抛出的 ValidationError 不在 request_params_to_args 收集 errors 的范围内
  （后者只收集字段级解析错误），故无法转换为 RequestValidationError → 422。

【解决方法】
  让 FastAPI 把模型作为"查询参数模型"解析：三个接口的参数声明由
  params: PageParams = Depends() 改为 params: Annotated[PageParams, Query()]，
  校验失败即被捕获并返回 422。同时补充 typing.Annotated 与 fastapi.Query 导入；
  因该参数不再有默认值，调整到签名首位。

  修改前（list_jobs 为例）：
      async def list_jobs(
          params: PageParams = Depends(),
          db_session: AsyncSession = Depends(get_db_session)
      ):

  修改后：
      async def list_jobs(
          params: Annotated[PageParams, Query()],
          db_session: AsyncSession = Depends(get_db_session),
      ):

  my_applications、list_job_applications 同步修改。

【验证】
  补充 pytest + httpx 测试（tests/ 目录，44 个用例全部通过）：
  page=0 / page=-1 / page_size=0 / page_size=-5 / page_size=101 均返回 422
  （修复前这些请求抛未捕获异常，实际为 500）。

问题 8（P2 · 安全性）：register 缺少密码强度校验
------------------------------------------------------------
【文件】schemas.py（auth.py 不变）

【问题描述】
  UserCreate.password 为任意 str，未做任何强度校验。用户可以注册
  "1"、"abc" 之类的弱密码，配合缺少速率限制的登录接口，存在被
  暴力破解/撞库的风险。

【问题原因】
  密码字段无长度与复杂度约束，仅由前端（若有）自行保证，后端未兜底。

【解决方法】
  在 schemas.py 的 UserCreate 中新增 field_validator("password") 校验器，
  规则如下（非法值由 Pydantic 拦截，返回 422）：
    - 长度至少 8 位
    - 同时包含字母和数字

  修改前：
      class UserCreate(BaseModel):
          username: str
          password: str
          role: Role = Role.student

  修改后：
      class UserCreate(BaseModel):
          username: str
          password: str
          role: Role = Role.student

          @field_validator("password")
          @classmethod
          def password_strength(cls, v: str) -> str:
              if len(v) < 8:
                  raise ValueError("密码长度至少为 8 位")
              if not any(c.isalpha() for c in v):
                  raise ValueError("密码必须包含字母")
              if not any(c.isdigit() for c in v):
                  raise ValueError("密码必须包含数字")
              return v

  说明：tests/ 中既有用例使用的密码 "pass123" 不满足新规则（无数字长度不足，
  实际 pass123 仅 7 位且无数字），已统一替换为 "password123" 以通过校验。

【验证】
  - "a1b2"（过短）→ 422
  - "12345678"（无字母）→ 422
  - "abcdefgh"（无数字）→ 422
  - "password123"（合法）→ 201
  补充 3 个强度校验测试用例，tests/ 目录共 47 个用例全部通过。

  3. .env / .env.example 新增 CORS_ORIGINS 配置项与注释说明。

  说明：保留 allow_credentials=True 下不能使用通配来源；生产部署时只需在

问题 12（P0 · 严重 bug）：requirements.txt 漏列 python-multipart
------------------------------------------------------------
【文件】requirements.txt

【问题描述】
  auth.py 的 login 接口使用 OAuth2PasswordRequestForm（基于 FastAPI 的 Form），
  解析表单数据依赖 python-multipart。该依赖此前既不在锁定前的 requirements.txt

    "Form data requires 'python-multipart' to be installed"

【问题原因】

  fastapi 的强制依赖，手动整理 requirements.txt 时被遗漏；本机能跑
  是因为该包恰好已安装在虚拟环境中（pip freeze 可见），掩盖了缺失。

【解决方法】
  requirements.txt 补充 python-multipart==0.0.32（与当前虚拟环境一致）。

【验证】
  pip freeze 中 python-multipart==0.0.32；新增依赖后 pytest 全量 47 用例通过。

问题 13（P1 · 并发安全/性能）：投递存在竞态，且外键列缺索引
------------------------------------------------------------
【文件】models.py、applications.py

【问题描述】
  1. 重复投递校验存在竞态（TOCTOU）：apply_job 先 SELECT 查重再 INSERT，
     两个并发请求都能通过查询（都查到"未投递"），随后都执行 INSERT，
     导致同一学生对同一岗位产生两条投递记录。
  2. Application.job_id / student_id 是 my_applications、list_job_applications
     两个列表接口的过滤列，但未建索引；MySQL InnoDB 会对外键自动建索引，
     但 SQLite（测试库）不会，且不应依赖数据库隐式行为。

【问题原因】
  - 应用层查重不是原子操作，无法在多请求并发下保证唯一性；
  - 高频过滤外键列未显式建索引。

【解决方法】
  1. models.py 给 Application 增加 (job_id, student_id) 唯一约束与两个外键列索引：

        __table_args__ = (
            UniqueConstraint("job_id", "student_id", name="uq_application_job_student"),
        )
        job_id = Column(..., index=True)
        student_id = Column(..., index=True)

  2. applications.py 保留原有的查重 SELECT 作为"快速路径"（命中即返回友好文案），
     但把唯一约束作为并发场景的最终兜底：INSERT 撞约束抛 IntegrityError 时，
     先 rollback 再返回 400，避免 500：

        try:
            await db_session.commit()
        except IntegrityError:
            await db_session.rollback()
            raise HTTPException(status_code=400, detail="你已投递过该岗位")

  说明：MySQL 中 create_all 不会修改已存在的表，需删表重建才能让新约束生效。

【验证】
  - 新增并发竞态测试 test_apply_duplicate_race：asyncio.gather 并发两次投递，
    结果恰为一个 201 + 一个 400，且 my_applications 总数仍为 1；
  - tests/ 目录 48 个用例全部通过；
  - MySQL 重建后 SHOW CREATE TABLE 确认存在
    UNIQUE KEY uq_application_job_student (job_id, student_id)
    及 ix_application_job_id / ix_application_student_id 两个索引。

问题 14（P1 · 功能完善）：投递列表只返回裸 ID，缺少关联对象信息
------------------------------------------------------------
【文件】models.py、schemas.py、applications.py、auth.py

【问题描述】
  ApplicationOut 此前仅返回 job_id / student_id 两个数字：
  - 学生查 my_applications 只拿到 job_id，无法直接得知岗位标题；
  - HR 查 list_job_applications 只拿到 student_id，无法得知投递人是谁、
    叫什么、如何联系，招聘闭环断裂。
  同时 User 模型只有 username / role，缺少姓名、邮箱等真实业务字段。

【问题原因】

改进 15（架构改进）：create_all 替换为 Alembic 数据库迁移
------------------------------------------------------------
日期：2026-08-31
【文件】migrations/（新增目录）、alembic.ini（新增）、migrations/env.py、
        migrations/versions/02767e84e64c_baseline_user_job_application_tables.py、
        main.py、tests/conftest.py、requirements.txt、README.md
        （代码中相关修改均以 【Alembic迁移】 注释标识）

【问题描述】
  此前应用启动时通过 lifespan 中的 Base.metadata.create_all 自动建表：
  - create_all 只能"从零建表"，不会修改已有表结构；模型改动（如问题 13/14
    加的唯一约束、新列）必须手动 DROP TABLE 重建，已有数据全部丢失；
  - 表结构无版本记录，多环境（开发/测试/生产）之间无法保证 schema 一致，
    也无法追溯某次结构变更是谁、何时、为什么引入；
  - 无法回滚：结构改错后没有标准的降级手段。

【问题原因】
  缺少数据库迁移（schema migration）机制，表结构演进依赖"删库重建"。

【解决方法】
  1. 引入 Alembic（异步模板）：alembic init -t async migrations，与项目的
     aiomysql 异步驱动保持一致；依赖锁定 alembic==1.19.1。

  2. migrations/env.py：
     - 连接串不在 alembic.ini 中写死（避免密码入库），改为从 config.DATABASE_URL
       读取并注入（密码含 % 时转义）；
     - target_metadata 指向 database.Base.metadata，并 import models 注册全部模型，
       使 autogenerate 能对比出完整表结构差异。
     注意：alembic.ini 需保持纯 ASCII——Alembic 用系统区域编码（中文 Windows
     为 GBK）读取该文件，写中文注释会导致 UnicodeDecodeError。

  3. 生成基线迁移 02767e84e64c（user/job/application 三张表，含
     uq_job_hr_title、uq_application_job_student 两个唯一约束与全部索引）。
     人工校订一处：server_default 由 SQLite 反射出的 '(CURRENT_TIMESTAMP)'
     统一改为 'CURRENT_TIMESTAMP'，保证在 MySQL 5.7+ 合法，且与 create_all
     在 MySQL 上的产物一致，避免后续 autogenerate 误报差异。

  4. main.py lifespan 移除 create_all 建表逻辑（保留 engine.dispose()），
     删除不再使用的 Base / models 导入；表结构升级改为显式执行
     alembic upgrade head（不随应用启动自动跑，避免生产多实例并发迁移）。

  5. tests/conftest.py 测试库有意保留 create_all（不走迁移）：建表快、
     与业务代码同步、隔离性好，且规避 SQLite/MySQL 方言差异对迁移脚本的
     干扰；迁移脚本正确性由对真实 MySQL 的验证保证。

【版本策略】
  - 全新环境：alembic upgrade head 从零建库；
  - 已有数据的环境（如本地 recruitment 库）：执行一次 alembic stamp head
    把当前库标记到基线版本（只新增 alembic_version 表，不动数据），
    之后模型再改动时 alembic revision --autogenerate 生成增量迁移。

【验证】
  1. 空库建库：临时 SQLite 与临时 MySQL 库（recruitment_alembic_check，
     验证后已删除）分别执行 alembic upgrade head 成功建出全部表；
  2. 一致性：对迁移建出的库再次 autogenerate，SQLite 与 MySQL 均为空 diff
     （迁移产物与 ORM 元数据一致）；
  3. 已有库：recruitment 库 stamp head 成功，alembic_version = 02767e84e64c；
  4. pytest 全量 51 个用例通过；
  5. 应用 lifespan 启动/关闭正常（不再执行建表）。

问题 16（P1 · 安全性）：JWT 过期时间使用本地时间，有效期失控
------------------------------------------------------------
日期：2026-08-31
【文件】auth.py  create_access_token 函数
        （代码中以 【修复】 注释标识）

【问题描述】
  exp 使用本地 naive 时间 datetime.now()，而 python-jose 编码 datetime 时
  会把它当作 UTC。东八区下 token 的实际有效期约为 配置值 + 8 小时：
  实测配置 60 分钟的 token，真实有效期约 540 分钟。登录凭证有效期失控。

【问题原因】
  naive datetime 被按 UTC 编码，本地时区偏移被叠加进 exp。

【解决方法】
  改为带时区的 UTC 时间：datetime.now(timezone.utc) + timedelta(minutes=EXPIRE_MINUTES)。

【验证】
  新增 test_token_expiry_encoded_as_utc：解码 exp 后与
  "当前 UTC 时刻 + EXPIRE_MINUTES" 比对，误差 < 2 分钟
  （修复前该断言偏差约 8 小时）。

问题 17（P1 · 严重 bug）：删除有投递记录的岗位返回 500
------------------------------------------------------------
【文件】jobs.py  delete_job 函数

【问题描述】
  application.job_id 外键默认 RESTRICT，岗位一旦存在投递记录，
  delete_job 提交时撞外键抛 IntegrityError，此前未捕获 → 500。
  而"岗位被投递过"是招聘系统的常态，删除功能基本不可用。

【问题原因】
  未处理外键约束失败，也未定义级联删除策略。

【解决方法】
  捕获 IntegrityError 后 rollback，返回 400 "该岗位已有投递记录，无法删除"。
  有意不做级联删除：静默删掉学生的投递记录会造成数据丢失，生产上应
  优先选择"下架/关闭岗位"语义。

【验证】
  test_delete_job_with_applications_returns_400（400 且岗位仍存在）；
  test_delete_job_without_applications_succeeds（无投递仍可正常 204 删除）。

问题 19（P1 · 严重 bug）：字符串字段无长度上限，超长输入返回 500
------------------------------------------------------------
【文件】schemas.py  UserCreate、JobCreate

【问题描述】
  username / name / email / title / description / requirements 均无
  max_length，而数据库列为 VARCHAR(80/100/120/1000)。MySQL 严格模式下
  超长插入抛 DataError → 500，而非 422。

【问题原因】
  Pydantic 层缺少与数据库列宽对应的长度约束，超长输入穿透到数据库。

【解决方法】
  各字段补充 Field(max_length=...)，上限与 models.py 列宽一一对齐
  （username/name: 80，email: 120，title: 100，description/requirements: 1000）。
  说明：Pydantic 的 max_length 按字符计，MySQL VARCHAR(n) 同样按字符计，
  两者语义一致；必填字段同时补 min_length=1 拦截空串。

【验证】
  test_register_username_too_long_returns_422（81 字符 → 422）；
  test_create_job_title_too_long_returns_422（101 字符 → 422）；
  test_create_job_description_too_long_returns_422（1001 字符 → 422）。

问题 20（P2 · 严重 bug）：超 72 字节密码注册返回 500
------------------------------------------------------------
【文件】schemas.py  UserCreate.password_strength

【问题描述】
  密码校验只有下限没有上限。bcrypt 5.0 对超过 72 字节的密码会抛
  ValueError（实测确认），注册/登录超长密码直接 500。

【问题原因】
  bcrypt 算法本身只取前 72 字节，python bcrypt 库 4.0+ 对超长输入
  显式抛错，而 schema 未限制上限。

【解决方法】
  密码强度校验器最前面增加按"字节"的上限检查：
  len(v.encode('utf-8')) > 72 → 422（按字节而非字符，兼顾中文等多字节字符）。

【验证】
  test_register_password_over_72_bytes_returns_422：60 个中文字符
  （180 字节）→ 422。
